## SILVER_AP_INVOICES dynamic table: SAP and Oracle combined

**Where it goes:** `COCO_WORKSHOP.PIPELINE_LAB.SILVER_AP_INVOICES`. The session's current schema is `SOURCE_DATA`, so I'll write the full name explicitly rather than rely on the current schema.

### What I found
- **Session:** role SYSADMIN, which owns the bronze tables and `PIPELINE_LAB`, using warehouse `COCO_WORKSHOP_WH`.
- **Change tracking:** it is **OFF** on `BRONZE_SAP_AP_INVOICES` and `BRONZE_ORACLE_AP_INVOICES`. A dynamic table needs it on its source tables to refresh incrementally.
- **Types:** the matching columns have identical data types, so no casting is needed beyond the placeholder columns described below.
- **Compile check:** the SELECT below compiled successfully. `UNION ALL` of two simple SELECTs is supported for incremental refresh.

### Steps
1. **Turn on change tracking** for both bronze tables:
   ```sql
   ALTER TABLE COCO_WORKSHOP.SOURCE_DATA.BRONZE_SAP_AP_INVOICES SET CHANGE_TRACKING = TRUE;
   ALTER TABLE COCO_WORKSHOP.SOURCE_DATA.BRONZE_ORACLE_AP_INVOICES SET CHANGE_TRACKING = TRUE;
   ```
2. **Create the dynamic table:**
   ```sql
   CREATE OR ALTER DYNAMIC TABLE COCO_WORKSHOP.PIPELINE_LAB.SILVER_AP_INVOICES
     TARGET_LAG = '1 hour'
     WAREHOUSE = COCO_WORKSHOP_WH
     REFRESH_MODE = AUTO
     INITIALIZE = ON_CREATE
   AS
   SELECT 'SAP' AS SOURCE_SYSTEM, INVOICE_ID, INVOICE_NUMBER, VENDOR_ID, VENDOR_NAME,
          INVOICE_DATE, DUE_DATE, INVOICE_AMOUNT, CURRENCY_CODE,
          PAYMENT_TERMS AS PAYMENT_TERMS_RAW,
          CASE PAYMENT_TERMS WHEN 'NET30' THEN 'NET30' WHEN 'NET60' THEN 'NET60' END AS PAYMENT_TERMS,
          PO_NUMBER, LINE_DESCRIPTION, GL_ACCOUNT, COST_CENTER, APPROVAL_STATUS, CREATED_AT,
          SAP_COMPANY_CODE AS COMPANY_CODE, SAP_DOCUMENT_TYPE,
          CAST(NULL AS VARCHAR(20)) AS ORACLE_SOURCE
   FROM COCO_WORKSHOP.SOURCE_DATA.BRONZE_SAP_AP_INVOICES
   UNION ALL
   SELECT 'ORACLE', INV_ID, INV_NUM, SUPPLIER_ID, SUPPLIER_NAME,
          INV_DATE, PAYMENT_DUE_DATE, TOTAL_AMOUNT, CURRENCY,
          TERMS_CODE,
          CASE TERMS_CODE WHEN 'N30' THEN 'NET30' WHEN 'N60' THEN 'NET60' END,
          PURCHASE_ORDER, DESCRIPTION, ACCOUNT_CODE, DEPT_CODE, STATUS, CREATION_DATE,
          ORACLE_ORG_ID, CAST(NULL AS VARCHAR(10)), ORACLE_SOURCE
   FROM COCO_WORKSHOP.SOURCE_DATA.BRONZE_ORACLE_AP_INVOICES;
   ```

### Design choices, including how the open questions from the comparison are handled
- **Column names:** the table uses SAP's names, which the questions in `AGENT_EVAL_SET` already expect. A new `SOURCE_SYSTEM` column tells the two systems apart, and the unique key is `(SOURCE_SYSTEM, INVOICE_ID)`.
- **Payment terms:** `PAYMENT_TERMS` is the only value I standardise (`N30` becomes `NET30`). The original value is kept in `PAYMENT_TERMS_RAW`. Any unrecognised code becomes NULL instead of being guessed.
- **Status:** `APPROVAL_STATUS` passes through unchanged. Whether Oracle's `VALIDATED` counts as approved stays an open question.
- **Cost center vs department:** SAP's cost center and Oracle's department both go into `COST_CENTER` unchanged. They are at different levels of detail; that is noted, not reconciled.
- **GL account and company/org:** `GL_ACCOUNT` and `COMPANY_CODE` keep each system's own codes, with no mapping between them.
- **Currency:** amounts stay in their original currency. There is no FX conversion, so totals across currencies are not meaningful.
- **Columns only one system has:** `SAP_DOCUMENT_TYPE` and `ORACLE_SOURCE` are kept and are NULL for the other system's rows.
- **Refresh settings:**
  - Target lag is `1 hour` because you didn't give a freshness requirement; it's easy to change later.
  - Refresh mode is `AUTO`, as the skill recommends while developing.
