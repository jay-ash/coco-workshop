**Fields that need normalization or default values**

No type changes are needed; the work is all in the values.
- **Payment terms:** SAP uses `NET30`/`NET60` and Oracle uses `N30`/`N60`. Map both to one standard form.
- **Currency:** both use ISO codes (USD, EUR, GBP), so only the column name changes.
- **Columns only one system has:**
  - SAP only: `SAP_DOCUMENT_TYPE`, which is `KR` in every row.
  - Oracle only: `ORACLE_SOURCE`, which is `AP_IMPORT` or `MANUAL`.
  - Either keep these as nullable columns specific to each source, or drop them. Don't give the other system a made-up value.
- **New `SOURCE_SYSTEM` column:** add it with `'SAP'` or `'ORACLE'`. The IDs don't collide today (`SAP-…` and `ORA-…`), but each system has its own vendor ID scheme (`V-…` and `S-…`). A unique key should therefore be `(SOURCE_SYSTEM, INVOICE_ID)`.
- **Company or org field:** if you map `SAP_COMPANY_CODE` (`1000`/`2000`/`3000`) and `ORACLE_ORG_ID` (`ORG-101`/`102`/`103`) into one column, keep the original values. Don't reformat them.

**Open questions to settle rather than assume**

1. **Status meanings.** SAP has `APPROVED`/`PENDING`. Oracle has `VALIDATED`/`APPROVED`/`PENDING`. Does Oracle's `VALIDATED` mean the same as approved, or is it an earlier step? The answer changes "invoice count by approval status".
2. **Cost center vs department.** SAP's `CC-ENG-01` is finer-grained than Oracle's `D-ENG`. Should they share one column, sit in separate columns, or go through a mapping table?
3. **GL account formats.** SAP uses `5100-10` and Oracle uses `A5100-40`. Is there a shared chart of accounts, or are these separate code sets that shouldn't be compared?
4. **What the amount includes.** Do `INVOICE_AMOUNT` and `TOTAL_AMOUNT` both mean gross amount including tax? "Total" might include tax or freight that SAP's amount doesn't.
5. **Header vs line level.** SAP has `LINE_DESCRIPTION`, which hints at invoice lines. Is each row a whole invoice in both systems? If some are lines, adding up amounts would double-count.
6. **Mixed currencies.** Should the Silver layer convert to one currency (at which rate and date), or keep the original currency and leave sums to be done per currency? The test questions currently add `INVOICE_AMOUNT` across all currencies.
7. **Timestamp time zones.** Both creation timestamps are stored without a time zone. Is each one in the source system's local time, or in UTC?
8. **Company/org mapping.** Do `1000`/`2000`/`3000` correspond to `ORG-101`/`102`/`103`? The currencies line up (USD, EUR, GBP), but that alone doesn't confirm it.
9. **Duplicate vendors.** Should the same vendor appearing in both systems be merged? There's no overlap in the sample, but you need a rule before adding Baan and Workday.

The `dynamic-tables` skill is the starting point for any work on Snowflake dynamic tables: creating them, changing them, monitoring, fixing problems, and tuning. It works out what you're trying to do, sends you to the right specialised workflow, and asks for your approval before changing anything.

- **Other workflows:** failure alerts, permission errors, and converting streams + tasks or dbt models into dynamic tables.

**What it expects from you**
- **Your request,** which it uses to route to a sub-workflow (create, alter, monitor, troubleshoot, and so on).
- **For creating a table:**

  - the transformation, as a SELECT
  - how fresh the data needs to be
  - whether the table is intermediate or final in a pipeline
  - which warehouse to use
- **For other workflows:** the name of the dynamic table or schema you mean.

provide use cases for dynamic tables as aposed to views/materialised views, any pros/cons

ASSISTANT:
Dynamic tables, views and materialized views all define data with a query. They differ in when that query actually runs.

| | View | Materialized view | Dynamic table |
|---|---|---|---|
| **When the query runs** | Every time someone reads it | Snowflake keeps the stored result up to date automatically | On a schedule, set by a target lag (minimum 1 minute) |
| **Freshness** | Always current | Always current; reads combine stored results with any changes not yet applied | Up to the target lag behind the source |
| **Query complexity** | Anything | Very limited: a single table, no joins, a restricted set of functions | Joins, unions, aggregations, window functions, mostly any SELECT |
| **Storage** | None | Yes | Yes |
| **Compute** | Each read, on the reader's warehouse | Background maintenance billed separately (serverless) | Each refresh, on the warehouse you assign |
| **Chaining** | Views can sit on views (re-computed on every read) | Can't be built on other materialized views or views | Built for chains: Snowflake works out the order and refreshes them together |
| **Edition** | All | Enterprise and above | All |

**When to use each**

*Dynamic tables* suit pipelines and transformations that are expensive to compute but don't need to be up to the second:
- Bronze → silver → gold layers, such as `SILVER_AP_INVOICES` combining SAP and Oracle.
- Joining or combining several sources and then cleaning or reshaping the data.
- Replacing streams + tasks, or scheduled `INSERT OVERWRITE` jobs, with a single declarative SELECT.
- Dashboards and BI that can tolerate data minutes or hours old but need fast reads.

*Views* suit cheap queries that must always be current:
- Light reshaping, renaming or filtering over tables.
- Hiding columns or restricting rows (secure views).
- Logic that is rarely queried, where storing the result isn't worth it.

*Materialized views* suit speeding up one heavy table that needs to be exactly current:
- Pre-aggregating or filtering a single large table that is queried often.
- Storing the table under a different clustering, so queries with other filters scan less.
- Faster queries over external tables.

**Pros and cons of dynamic tables**

Pros:
- **Declarative:** you write the SELECT and Snowflake handles scheduling, dependencies and refreshes.
- **Incremental refresh:** where possible, it processes only rows that changed rather than recomputing everything.
- **Handles complex logic** that materialized views can't, such as joins and unions.
- **Fast reads:** queries hit stored results, not the source tables.
- **Visible operations:** refresh history, pipeline graphs and failure states are all available to inspect.
- **Predictable cost:** compute runs on the warehouse you assign, and you can choose the lag.

Cons:
- **Not real-time:** data is at best about 1 minute behind, and typically more, depending on the lag you set.
- **Costs storage and warehouse compute,** even for refreshes that turn out to have nothing to do.
- **Some queries can't refresh incrementally** (for example certain non-deterministic functions or complex patterns), which forces slower full refreshes.
- **Change tracking is required on the source tables,** and turning it off later breaks refreshes.
- **Restrictions:**
  - no procedural logic or side effects
  - one output table per definition
  - external tables can't be sources
  - a view can't sit between two dynamic tables
- **Rebuilds:** `CREATE OR REPLACE` reloads the table from scratch and can trigger rebuilds of incremental tables downstream.

**Rule of thumb**
- **Must always be current and cheap to compute:** use a view.
- **Must always be current, comes from one table, and is expensive to compute:** use a materialized view.
- **A multi-step or multi-table transformation that can lag slightly:** use a dynamic table.

I wrote this from general Snowflake knowledge and didn't check it against the current documentation. The minimum lag and the materialized-view restrictions in particular can change between releases.

### 3. Failure and staleness patterns to watch

- **Source columns renamed or dropped.** The query lists every source column by name, so a renamed or dropped column fails the refresh. This is the most likely failure. Watch for `FAILED` in the refresh history.
- **Change tracking turned off** on either bronze table, which breaks refreshes.
- **Source tables replaced.** `CREATE OR REPLACE` on a bronze table (as `00_sample_data.sql` does) creates a new table, which forces Silver to rebuild from scratch and can break incremental refresh until it does. Re-running the loader is the realistic trigger here.
- **Warehouse problems.** If `COCO_WORKSHOP_WH` is dropped, suspended with auto-resume off, or the owning role loses USAGE on it, refreshes fail or get skipped and the table goes stale.
- **Auto-suspension.** Repeated failures can make Snowflake suspend the table, and it then stops refreshing until resumed.
- **Refresh mode drift.** Snowflake picked `ADAPTIVE`. If a future change (for example a non-deterministic function) forces `FULL` refreshes, it still works but costs more. Check `refresh_action` and `refresh_mode_reason`.
- **Unrecognised payment terms.** New codes (for example `NET45`, or Baan and Workday codes) become NULL in `PAYMENT_TERMS`. Nothing fails, so this needs a data check rather than refresh monitoring.
- **Missed lag.** If `time_within_target_lag_ratio` drops below about 0.9, refreshes are taking longer than the lag allows or the warehouse is queued.
- **Passing failures downstream.** Once a Gold table exists, a Silver failure shows up there as `UPSTREAM_FAILED`.

- [ ] Keep change tracking **on** for every source, including Baan and Workday when they're added.
- [ ] Change the Silver definition with `CREATE OR ALTER`, not `CREATE OR REPLACE`, so it isn't rebuilt from scratch unnecessarily.
- [ ] Don't re-run `00_sample_data.sql` against a live pipeline. Use `INSERT`/`MERGE` into the bronze tables instead of replacing them.
- [ ] Keep listing columns explicitly, as now, and treat changes to bronze columns as changes that need coordinating.
- [ ] Set `TARGET_LAG = DOWNSTREAM` on Silver once a Gold table exists, and give only Gold a time-based lag.
- [ ] Check periodically that refreshes are still incremental (`refresh_mode`, `refresh_action`).
- [ ] Watch `time_within_target_lag_ratio`, and refresh errors with `ERROR_ONLY => TRUE`.
- [ ] Set up a failure alert; the skill has an alerting workflow for this.
- [ ] Add a data check that `PAYMENT_TERMS IS NULL` counts stay at zero, plus row counts and totals that match bronze.
- [ ] Before applying an ALTER, preview whether it would trigger a rebuild with `EXPLAIN CHANGES`; the skill has a workflow for this too.
- [ ] Give `COCO_WORKSHOP_ROLE` (or whoever reads the table) `SELECT` on Silver, and make sure the owning role keeps USAGE on the warehouse.

## 3. Failure and staleness patterns to watch for

| Pattern | Signal | Typical cause |
|---|---|---|
| Schema change in a bronze table | `FAILED` with a compilation error, or a `REINITIALIZE` action | A column in the SAP or Oracle bronze table was renamed, dropped or changed type |
| Change tracking turned off | Refreshes fail | Someone ran `ALTER TABLE ... SET CHANGE_TRACKING = FALSE` on a source table, or recreated it |
| Silent switch to full refresh | `refresh_action = FULL` appears repeatedly; `refresh_mode_reason` gets filled in | A query edit introduced a construct that can't be refreshed incrementally. This matters more because the mode is `ADAPTIVE`. |
| Suspended | `scheduling_state = SUSPENDED` | Several refreshes in a row failed, or someone suspended it manually. It won't resume on its own after failures. |
| Warehouse problems | Refresh queued or skipped; lag rises | `COCO_WORKSHOP_WH` was dropped, suspended with auto-resume off, or the role lost USAGE on it |
| Lag growing | `time_within_target_lag_ratio < 1`; `maximum_lag_sec` > 3600 | A heavy bronze load made refreshes slow, or the warehouse is undersized or queued |
| Ownership or permission errors | `Insufficient privileges` | The owning role lost SELECT on a bronze table |
| Data quality hidden by `UNION` | Refreshes succeed but row counts look wrong | Duplicate invoice IDs across SAP and Oracle, unmapped currency or status values, nulls in key fields. The table won't flag these itself. |

## 4. Best-practices checklist

- **Set the lag to `DOWNSTREAM`** once Gold exists, and put the business freshness requirement on Gold.
- **Check weekly** that the refresh actions are mostly `INCREMENTAL` or `NO_DATA`, and investigate any `FULL` or `REINITIALIZE`.
- **Use a dedicated XS warehouse** with auto-suspend set to 60 seconds, owned by a role that keeps SELECT on both bronze tables.
- **Set up an alert** on `state = 'FAILED'` or `scheduling_state = 'SUSPENDED'`.
- **Before changing a bronze table's schema or the table's own query**, preview the impact with `EXPLAIN CHANGES` or `CREATE OR ALTER`. This avoids unexpected reinitialisation.
- **Keep change tracking on** for both source tables, and never recreate them in place with `CREATE OR REPLACE`.
- **Run data-quality checks:** unique invoice IDs per source system, non-null vendor, amount and date, and valid currency codes.
- **After a bulk load you need visible immediately**, run `ALTER DYNAMIC TABLE ... REFRESH` instead of tightening the lag.
- **Keep the table's DDL in version control**, and document the SAP-to-Oracle column mapping.

Everything I ran was read-only; nothing was changed. The checks in section 2 could run as a daily `cortex automation` that flags failures, suspensions or unexpected full refreshes, if you'd like that.

## Guardrails

| Guardrail | Why |
|---|---|
| **Never add amounts across currencies.** Always group by `CURRENCY_CODE`, and decline "total spend in USD" (FX rates sit in Gold, under BR-002). | The table holds USD, GBP and EUR with no conversion. A single total would be wrong. |
| **No payment questions.** Answer "paid?" or "days to pay" with "not available in this dataset". | There's no payment status or paid-date column. "Approved" doesn't mean "paid". |
| **Compare GL accounts only within one source system.** | Each system has its own numbering scheme (BR-006). Comparing GL codes across systems is meaningless until the Phase 2 chart-of-accounts mapping. |
| **State the as-of date.** Report the data's freshness, and tell users the latest invoice is 2025-06-01. | The table refreshes on a 1-hour lag. It also holds only 2025 sample data, so "past due" against today (Nov 2026) would flag everything. |
| **Use the standardised columns:** `APPROVAL_STATUS` and `PAYMENT_TERMS`, not the `*_RAW` versions. Mention a NULL status as "unmapped" rather than leaving it out silently. | `*_RAW` holds each source system's own values, such as VALIDATED, POSTED or In Review. |
| **Only answer from this table.** Questions about POs, receipts, vendor master data or contracts get redirected. | The point is to stay grounded in curated data. |
| **Invoices over $500k get no special treatment.** If asked, say the flag is handled by a data-quality check, not by the agent. | BR-004 assigns it to a data-quality check, and the threshold assumes USD amounts that Silver doesn't have. |

## Best practices

**Warnings**
- **No verified queries.** This is the biggest gap in the score. *Now addressed, see below.*
- **`OUTSTANDING_INVOICE_AMOUNT` duplicates `TOTAL_INVOICE_AMOUNT`.** Both are `SUM(INVOICE_AMOUNT)`. Two metrics with identical logic but different names invite inconsistent answers, and "unpaid" looks like real data when it isn't. Better: drop it and let Cortex Analyst say payment data isn't available, or redefine it once a payments source exists.
